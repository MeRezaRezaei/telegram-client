# Night W1-1 — Ingest-failure retry cap (P3 carried)

Repo: telegram-client @ bc31d27 (master). Carried P3-review: an entry
that DECODES fine but whose ingest() persistently throws (e.g. unknown
constructor deep in the payload against this build) wedged the consumer
group forever — the exception escaped consumeOnce(), the entry was
never acked and never dead-lettered (the plan only specced
decode-poison).

## Fix (TDD)

- `src/Bus/IngestConsumer.php`:
  - consumeOnce() now drains this consumer's OWN pending entries
    (xreadgroup id `0`) before the `>` batch — retries can't be starved
    by fresh traffic, and a crash mid-batch still redelivers the
    un-acked tail;
  - the ingest path (client ingest + onStored hook) is wrapped in a
    catch (\Throwable): below the cap the entry stays un-acked and is
    retried on the next consumeOnce() cycle; after 3 consecutive
    throws (self::INGEST_ATTEMPTS, per-entry counter in a bounded
    in-memory array, cap 1024, cleared on success) the entry is
    dead-lettered with `reason=ingest-failed` + `error` + original
    fields, then acked — the group keeps moving;
  - decode-poison dead-letters stay byte-verbatim (untagged), per the
    original spec; retry pacing is free: the loop's 100ms idle backoff
    fires because a deferred retry reports processed=0.
- Semantics documented in the class docblock + docs/bus.md poison
  section (incl. the honest caveat: the strike counter is
  per-process/instance — the loop/daemon reaches the cap in-process; a
  restarted process restarts the count, which only delays the
  dead-letter, never the group's progress).
